# 架构决策记录（ADR）

记录影响面较大、以后可能被重新讨论的取舍。每条包含：背景、候选方案、决定与后果。实现细节见 [DESIGN.md](../DESIGN.md)。

---

## ADR-001：以 DSH 原生 bundle 交付，而不是独立站点或外部服务

**背景**：需求是「左侧栏固定入口 + 多端可用」。DSH 已提供 slot 系统与插件加载器。

**候选**：①原生 bundle（`dsh.bundle.patch` + `dsh.client`）；②独立 Web 站点，用 iframe 嵌入 DSH；③外部守护进程 + 反向代理注入。

**决定**：原生 bundle。宿主半用 Cordis 生命周期，客户端半注册 `sidebar.panellist` 与 `main`。

**后果**：入口、主题、权限、更新都跟随 DSH；不能用其它技术栈重写面板；宿主升级需回归测试。iframe 站点方案被否，因为登录/主题/移动端体验都会割裂。

## ADR-002：面板与宿主使用 Connection RPC，而不是 Typert Remote 或自建 HTTP

**背景**：面板需要调用宿主读写节点、令牌、Hub 状态。

**候选**：①`@deepseek-ai/dsh-typert-protocol` 的 Typert Remote；②`ctx.connection.rpc.handle` 注册认证通道；③插件自建 HTTP + 自定义会话。

**决定**：Connection RPC（`/node-monitor-rpc`）。每个请求校验 `peer.principal.kind === 'owner'`。

**后果**：复用 DSH Cookie 认证，不用自管会话；通道只在 DSH 内可用，外部程序无法直接调用；Typert 方案需要额外 manifest 与代码生成，收益不足（历史经验：profile 未加载 remote 行会导致服务不可见）。自建 HTTP 会重复实现认证，已否决。

## ADR-003：跨节点通信使用 Bearer HTTP，不复用 DSH 会话 Cookie

**背景**：节点之间需要互相读取状态，且不能要求对方暴露 DSH 登录令牌。

**候选**：①复用 DSH Web 会话；②每节点 API token + 插件自有 HTTP 端点；③mTLS。

**决定**：每节点 `agentToken`（完整权限）与 `statusToken`（只读）双令牌；`Authorization: Bearer`。

**后果**：节点可独立授权/轮换/撤销；令牌泄露面小于 DSH 登录态；需要自行实现限流、恒时比较、HTTPS 终止；mTLS 对家庭网络过重。

## ADR-004：插件自监听 45873，而不是要求 DSH `--host 0.0.0.0`

**背景**：v0.4 之前跨机访问失败，主要原因是 DSH 只监听 `127.0.0.1`，而修改 DSH 启动参数对普通用户门槛高。

**候选**：①要求用户 `--host <IP>`；②复用 DSH 3081 并让用户配置 Host 白名单；③插件自建 agent 监听。

**决定**：插件在 `0.0.0.0/::` 监听 `45873`，只暴露状态/控制/配对/Hub 端点。

**后果**：零配置可用；绕过 DSH 的 Host 校验；需要单独考虑防火墙与端口暴露（默认建议只开 45873）；DSH 网页的「打开/内嵌」仍需 3081 可达。

## ADR-005：UDP 发现只广播公开身份，令牌单独校验

**背景**：局域网自动发现要「装完即用」，但又不能让同网段任意主机接管。

**候选**：①广播含令牌（免配对）；②广播身份，接入时出示令牌；③mDNS/DNS-SD + 令牌。

**决定**：广播 `id/label/port/version/ap`，不含令牌；接入/自动配对必须再走 `/pair` 并校验令牌。

**后果**：发现不等于授权；同网段可伪造公告，但拿不到令牌无法接入；企业 WiFi 的广播隔离会让发现失效，仍支持手动地址。

## ADR-006：自动配对只交换只读令牌

**背景**：v0.5 的自动配对为了「零配置」返回了完整 `agentToken`，任何能发 UDP 公告的主机都能拿到控制权（v0.6.3 安全审核发现）。

**候选**：①继续返回完整令牌；②自动配对只交换 `statusToken`；③取消自动配对。

**决定**：自动配对只交换 `statusToken`（只读、无会话明细、控制关闭）。要控制必须人工复制完整令牌。

**后果**：自动组网默认安全；会话明细需要手动接入；旧版本保存的完整令牌需轮换；引入第二把令牌的生命周期与轮换逻辑。

## ADR-007：远程主节点采用反向轮询，而不是反向 WebSocket

**背景**：PC 在 NAT 后，公网服务器不能主动连 PC。

**候选**：①PC 主动连服务器的 WebSocket 隧道；②PC 定期 POST 状态 + 长轮询取命令；③要求用户自建 frp/Tailscale。

**决定**：3 秒 POST `/hub/push`，响应中带回排队命令；结果再 POST `/hub/result`。

**后果**：实现简单、穿 NAT/代理稳定、无需自写 WS 帧；实时性 3 秒级、命令 20 秒过期；大量节点时 Hub 轮询压力随节点数线性增长（当前上限 128 peer）。

---

## ADR-008：运维控制默认关闭，且必须 dry-run + confirm + 审计

**背景**：远程启停插件可能让节点不可用（例如禁用 DSH 自身插件）。

**候选**：①默认开启、一键操作；②默认关闭、显式开启；③只读不控制。

**决定**：`allowControl` 默认关；开启后仍要 `dryRun`（默认 true）与 `confirm`；`restart` 再需 `allowRestart`；每次调用写 `audit.jsonl`。

**后果**：安全但操作多一步；适合自有设备；不适合多租户托管；重启导致的失联风险由用户显式承担。

---

## ADR-009：邀请/加入令牌放在 URL `#` 片段

**背景**：需要「复制一条链接/扫码」完成接入，但令牌不能进入服务器日志、Referer。

**候选**：①查询参数 `?token=`；②路径段 `/j/<token>`；③`#` 片段，由前端解析。

**决定**：`#node-monitor-join=` / `#node-monitor-add=`，页面读取后立即 `history.replaceState` 清除。

**后果**：片段不会发送给服务器；二维码/链接可安全截图；链接本身仍是凭据，需要「轮换令牌即失效」；不支持服务端直接处理链接（必须由面板 JS 解析）。

## ADR-010：二维码本地生成

**背景**：手机扫码是最自然的接入方式。

**候选**：①第三方 QR 图片 API；②前端库；③宿主内置编码器生成 SVG。

**决定**：宿主内置 `lib/qrcode.js`（qrcode-generator，MIT）生成 SVG，经 `hubJoin` 返回。

**后果**：令牌不出本机、离线可用；客户端体积增加约 56KB；需在 `files` 中包含该文件并遵守 MIT 许可。

## ADR-011：状态用单文件 JSON，而不是 SQLite/内存数据库

**背景**：需要持久化节点、设置、告警确认、令牌引用。

**候选**：①`state.json` + `secrets.json`；②SQLite；③DSH storageDomain。

**决定**：两个 0600 JSON 文件，原子写入（tmp + rename），状态与密钥分离。

**后果**：零依赖、易备份/迁移；并发写依赖单进程；状态规模上限（节点 64、告警确认 500）足够个人/小团队；不能保存历史趋势（路线图）。

---

## ADR-012：`apply()` 非阻塞，客户端加错误边界

**背景**：早期版本 `apply()` 返回等待宿主服务的 Promise，安装/热重载时表现为卡死或整站 502。

**候选**：①同步等待服务；②异步后台初始化 + 重试；③完全懒加载。

**决定**：`apply()` 立即返回 disposer；初始化后台执行；Web 集成 1.5 秒窗口，RPC 注册 5 次重试；客户端 `PanelBoundary` 隔离渲染错误。

**后果**：宿主服务未就绪时插件降级而不是崩溃；功能可能延迟数秒可用；需要面板显示「未就绪」状态与刷新入口。

---

## ADR-013：不做完整聊天 UI，不代理 DSH 协议

**背景**：用户希望「像正常 DSH 一样发消息」。但重写聊天 UI 需要跟随 DSH 会话协议，维护成本高且容易破坏体验。

**候选**：①在面板内实现聊天；②跳转/内嵌真实 DSH 界面；③反向代理 DSH 全站。

**决定**：只做「打开/内嵌真实 DSH」：一次性票据 302 到登录页；同源时 iframe。完整聊天仍用 DSH 原生界面。

**后果**：保真、零协议维护；跨源无法内嵌（需子域反代）；「打开」依赖用户保存的 DSH 登录地址；插件不接触会话内容，符合安全边界。

---

## ADR-014：尽量零运行时依赖

**背景**：插件要跨 Windows/macOS/Linux 安装，依赖越少越稳。

**候选**：①引入 zod/ws/express 等；②只用 Node 内置模块；③仅内置必要的单个库。

**决定**：运行时依赖为空，仅内置 MIT 的 `qrcode.js`；HTTP 用 `node:http`，发现用 `node:dgram`，没有 WebSocket。

**后果**：安装体积小、无供应链风险；需要自写校验与路由；QR 库需随包分发并保留许可声明。
